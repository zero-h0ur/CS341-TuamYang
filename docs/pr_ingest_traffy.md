## Summary

เพิ่มระบบดึงและเตรียมรายงาน Traffy เพื่อให้ทีมใช้จับคู่พื้นที่และวิเคราะห์สัดส่วนรายงานน้ำท่วมในกรุงเทพฯ
รองรับทั้งการดึงข้อมูลรายวัน การอัปเดตรายชั่วโมงในช่วงฝนหนัก และการดึงข้อมูลย้อนหลัง (backfill)
พร้อมกติกาอ่านข้อความเพื่อแยกรายงานที่เกี่ยวกับน้ำท่วม แม้ช่องประเภทปัญหาจากต้นทางจะว่าง

ข้อมูลที่ได้จะแยกตามวันในเวลาไทย ตัดรายงานซ้ำ และเก็บต้นฉบับไว้ตรวจสอบย้อนหลัง
รายงานทุกประเภทยังคงอยู่ในชุดข้อมูล เพื่อให้คำนวณสัดส่วนรายงานน้ำท่วมเทียบกับรายงานทั้งหมดตามคำถาม Q2 ได้

## Changes

- **ดึงข้อมูลรายวันและรายชั่วโมง** — โหมดรายวันดึงรายงานของเมื่อวานตามเวลาไทย
  ส่วนโหมดรายชั่วโมงอัปเดตรายงานของวันนี้ถึงเวลาที่เริ่มรัน และระบุว่าข้อมูลของวันนี้ยังไม่ครบวัน
  ในชั่วโมงแรกหลังเที่ยงคืนจะอัปเดตข้อมูลของเมื่อวานด้วย เพื่อเก็บรายงานที่เพิ่มเข้ามาช่วงท้ายวัน
  หาก API ขัดข้องชั่วคราว ระบบจะลองเรียกใหม่ตามจำนวนครั้งที่กำหนด
  (`src/traffy_client.py`, `src/ingest_traffy.py`)
- **ดึงข้อมูลย้อนหลังและรันต่อได้** — ช่วงเริ่มต้นคือ `2022-06-01` ถึงเมื่อวาน
  ใช้ `--max-days` จำกัดจำนวนวันที่ประมวลผลใหม่ในแต่ละรอบได้ ระบบจะข้ามวันที่ทำสำเร็จและตรวจสอบแล้ว
  พร้อมแจ้งวันที่ควรรันต่อ หากพบข้อผิดพลาดจะหยุดที่วันนั้น เพื่อให้แก้ไขแล้วเริ่มต่อจากจุดเดิมได้
  (`src/backfill_traffy.py`)
  เพิ่มตัวรันเต็มช่วง `scripts/run_traffy_backfill.py` ทำพร้อมกันได้ไม่เกินสี่วัน
  โดยควบคุมความถี่เรียก API รวมทั้งงาน มีไฟล์ติดตามความคืบหน้าและตรวจข้อมูลทุกวันก่อนสรุปว่าครบ
- **แยกรายงานน้ำท่วมจากข้อความ** — ตรวจคำอย่าง “น้ำท่วม” และ “น้ำขัง” ร่วมกับบริบทของประโยค
  เช่น การปฏิเสธว่าไม่มีน้ำท่วมหรือการขอให้ป้องกันน้ำท่วม
  ผลแบ่งเป็นน้ำท่วม (`flood`), ไม่ใช่น้ำท่วม (`non_flood`) และไม่แน่ชัด (`uncertain`)
  พร้อมเก็บเหตุผลและเวอร์ชันของกติกาไว้ตรวจสอบ (`src/traffy_filter.py`)
- **เตรียมข้อมูลให้ขั้นตอนถัดไปใช้ได้** — เก็บเวลาทั้ง UTC และเวลาไทย
  ตัดรายงานซ้ำด้วยรหัสรายงาน `ticket_id` และบันทึกข้อมูลดิบจาก API ทุกหน้า
  เมื่อรันเสร็จจะมีไฟล์สรุปผล (manifest) ระบุสถานะ จำนวนรายงาน และค่า hash สำหรับตรวจสอบว่าเนื้อหาตรงกัน
- **เตรียมตัวอย่างสำหรับตรวจคุณภาพกติกา** — สุ่ม 100 รายงานด้วย seed `341` เพื่อให้สุ่มซ้ำได้ชุดเดิม
  มีแบบฟอร์มให้คนอ่านและกรอกผลตรวจ พร้อมคำสั่งคำนวณ precision
  และป้องกันการสุ่มชุดใหม่ทับงานที่ตรวจไว้แล้ว (`scripts/review_traffy.py`)
- **เตรียมการใช้งานบน AWS** — มีสคริปต์สร้างแพ็กเกจและติดตั้ง Lambda
  พร้อม EventBridge สำหรับตั้งเวลาเรียกรายวันหรือรายชั่วโมง โดยเลือกเปิดใช้งานได้
  ตัวดึงข้อมูลใช้ส่วนจัดเก็บร่วมของทีม รองรับทั้งบนเครื่องและ S3 พร้อมทดสอบอัตโนมัติบน GitHub Actions
  (`infrastructure/`, `scripts/package_traffy.py`, `tests/`)

ชุดทดสอบครอบคลุมการดึงข้อมูลหลายหน้า การรับมือเมื่อ API ล้มเหลว รอยต่อวันตามเวลาไทย
การตัดรายงานซ้ำ การกรองข้อความ การอัปเดตระหว่างวัน การดึงย้อนหลังต่อจากรอบก่อน และการคำนวณผลตรวจคุณภาพ

สำหรับตัวอย่าง 100 รายงาน ได้ให้ AI อ่านและจัดประเภทเบื้องต้นโดยไม่แสดงผลของกติกาขณะอ่าน
ผลตรงกับกติกา **94 รายการ** ส่วนอีก 6 รายการ AI ยังจัดประเภทไม่ได้แน่ชัด
ใน 78 รายการที่กติกาจัดเป็นน้ำท่วม AI จัดเป็นน้ำท่วม 76 รายการ ไม่ใช่น้ำท่วม 0 รายการ
และยังไม่แน่ชัด 2 รายการ

Precision คือสัดส่วนของรายงานที่กติกาจัดเป็นน้ำท่วมแล้วตรงกับผลตรวจอ้างอิง
เมื่อยังมี 2 รายการที่ตัดสินไม่ได้ จึงยังสรุปเป็นค่าเดียวไม่ได้ โดยมีค่าที่เป็นไปได้ระหว่าง **97.44%–100%**
ตัวเลขนี้อิงผลอ่านเบื้องต้นจาก AI **ยังไม่ได้ตรวจยืนยันโดยคน**
เตรียมไฟล์ที่รวมข้อความกับช่องกรอกผลให้คนอ่านได้ในที่เดียวแล้ว ดูวิธีตรวจใน `docs/traffy_review_100.md`

## Deployment Boundary

- **การดึงข้อมูลจริงข้างต้นทำบนเครื่อง ยังไม่ได้เรียก Lambda หรือเขียนข้อมูลลง S3 จริง**
  สคริปต์ติดตั้งและตั้งเวลาผ่านการทดสอบด้วย AWS จำลองแล้ว
  เจ้าของงานขอทำขั้นตอนตั้งค่า AWS ภายหลัง จึงยังรอการติดตั้งและแนบผลรันจริงจากบัญชีของทีม
- **กำลังดึงข้อมูลย้อนหลังครบช่วง `2022-06-01` ถึง `2026-11-08` รวม 1,622 วัน**
  เริ่มรันจริงแล้วและจะข้ามวันที่มีข้อมูลซึ่งตรวจสอบผ่าน ผลตรวจ ณ เวลาเก็บหลักฐานอยู่ใน
  `evidence/traffy/full_backfill/progress_snapshot.json` ส่วนสถานะล่าสุดบนเครื่องอยู่ใน
  `data/checkpoints/traffy/runs/full_history/progress.json`
  จะยืนยันว่าครบเมื่อผลตรวจสุดท้ายมี `range_complete: true` และไม่มีวันที่ขาด
  ดูคำสั่งรันต่อและตรวจผลใน `docs/traffy_full_backfill.md`
- **API มีข้อจำกัดที่ต้องเก็บไว้ประกอบการอ่านผล** — รับช่วงเวลาเป็นวันที่ UTC
  และแจ้งยอดรวมมากกว่าจำนวนแถวที่ส่งกลับจริง โดยต่างกัน 40, 47 และ 69 รายการในสามวันที่ทดสอบ
  ระบบจึงดึงต่อจน API ส่งหน้าว่างกลับมาและบันทึกความต่างไว้ ยังยืนยันไม่ได้ว่าครบตามยอดที่ต้นทางแจ้ง

เวลาของรายงานคือเวลาที่ประชาชนแจ้งปัญหา ส่วนผลกรองคือการจัดประเภทจากข้อความ
การนำไปวิเคราะห์จึงต้องคำนึงว่ายังไม่ได้ยืนยันเวลาเริ่มท่วมหรือสภาพน้ำท่วมที่บ้านแต่ละหลัง

PR นี้ใช้ `feature/ingest-thaiwater` เป็นฐาน เพราะใช้ส่วนจัดเก็บข้อมูลร่วมกัน
เมื่อรวม branch ฐานเข้า `main` แล้ว ให้เปลี่ยนฐานของ PR นี้ตาม
หากรวมแบบ squash ต้องย้ายเฉพาะ commit ของ Traffy ไปต่อบน `main` ก่อน เพื่อไม่ให้ประวัติงานฐานซ้ำซ้อน

## Downstream Handoff

- **ทีมจับคู่พื้นที่ (Reference & Spatial Join):** อ่านรายงานจาก `incoming/traffy/`
  ใช้ `longitude` / `latitude` จับคู่แขวง และใช้ `ticket_id` อ้างอิงรายงาน
  รายงานที่พิกัดขาดหรือผิดรูปแบบยังถูกเก็บไว้ พร้อม `quality_flags` ระบุปัญหา
  เพื่อให้ตรวจได้ว่าจับคู่พื้นที่สำเร็จมากน้อยแค่ไหน
- **ทีมควบคุมขั้นตอนและตรวจข้อมูล (Orchestration & Validation):** รอไฟล์สรุปผลเป็น `SUCCESS`
  แล้วตรวจว่าเลขรอบการรัน (`batch_id`) และค่า `records_sha256` ตรงกับชุดข้อมูลก่อนใช้ต่อ
  หากได้รับแจ้งว่ามีไฟล์ใหม่ใน S3 ก่อนที่ไฟล์สรุปผลจะเขียนเสร็จ ให้รอแล้วตรวจอีกครั้ง
  ส่วน `_SUCCESS.json` สำหรับยืนยันผลของขั้นตอนถัดไปยังเป็นหน้าที่ของทีมนี้
- **ทีมวิเคราะห์ (Curated & Analysis):** ใช้ `report_date_bkk` / `report_hour_bkk` รวมข้อมูลรายชั่วโมง
  คำนวณ Q2 โดยนับรายงานที่ `is_flood_report IS TRUE` เทียบกับรายงานทั้งหมด
  และแสดงจำนวนที่ยังไม่แน่ชัดแยกไว้ ไฟล์ใน `staged/traffy/` มีเฉพาะรายงานน้ำท่วม
  จึงต้องใช้ชุดรายงานทั้งหมดจาก `incoming/traffy/` ในการหาตัวหาร

รายละเอียดฟิลด์และเงื่อนไขการรับส่งข้อมูลอยู่ใน `reference/traffy_schema_contract.md`
