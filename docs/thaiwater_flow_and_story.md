## 2. บทสรุปภาพรวมของงาน (Executive Summary)

ระบบนี้ทำหน้าที่เป็น **"ท่อส่งข้อมูลน้ำและฝน"** ให้กับระบบเตือนภัยน้ำท่วม TUAMYANG โดยเชื่อมต่อดึงข้อมูลจาก **คลังข้อมูลน้ำแห่งชาติ (สสน. / ThaiWater)** นำมาจัดเก็บลงใน **AWS S3 Data Lake** เพื่อให้เพื่อนร่วมทีมนำไปวิเคราะห์และทำนายน้ำท่วมต่อได้อย่างถูกต้อง

### สรุปสิ่งที่ทำเสร็จสมบูรณ์ใน Issue และ PR นี้:
1. **ระบบดึงข้อมูลสดอัตโนมัติ (Live Serverless Ingestion):**
   - ใช้ **AWS Lambda** (`src/ingest_thaiwater.py`) ดึงระดับน้ำสด 8 สถานีคลองหลักทุก 15 นาที และดึงปริมาณฝนสด 15 สถานีทุก 1 ชั่วโมง
   - ตั้งเวลาทำงานอัตโนมัติด้วย **AWS EventBridge Scheduler**
   - คำนวณยอดฝนสะสม 24 ชั่วโมงจากอนุกรมเวลารายชั่วโมงจริง และมีระบบรองรับกรณีบางสถานีส่งข้อมูลช้าหรือไม่ตอบสนอง (ระบบจะบันทึกสถานะ `PARTIAL` และเก็บข้อมูลสถานีที่เหลือได้ตามปกติ ไม่ค้างหรือล่มทั้งระบบ)
2. **จัดเก็บข้อมูล 2 โซนบน AWS S3 (Dual-Zone S3 Storage):**
   - โซนที่ 1: `incoming/thaiwater/` — เก็บเฉพาะไฟล์รอบล่าสุด สำหรับส่งต่อให้ระบบคำนวณความเสี่ยงหยิบไปใช้ทันที
   - โซนที่ 2: `raw/thaiwater/` — เก็บสำเนาข้อมูลดิบทั้งหมดไว้ถาวร แยกตามวัน (`dt=YYYY-MM-DD`) ห้ามแก้ไข เพื่อใช้เป็นประวัติศาสตร์
3. **ระบบดึงข้อมูลย้อนหลัง 5 ปี (Historical Backfill 2022–ปัจจุบัน):**
   - โปรแกรม `src/backfill.py` ดึงข้อมูลระดับน้ำย้อนหลังแบบละเอียดทุก 10 นาที ตั้งแต่ต้นปี 2022 จนถึงปัจจุบัน
   - สกัดค่าความสูงของตลิ่ง (`min_bank`) ออกมาจากระบบโดยตรง เพื่อใช้วัดว่าน้ำใกล้ล้นตลิ่งแค่ไหน
4. **ระบบจดจำสถานะงาน (Checkpoint) ทนต่อเวลาตัดรอบของ AWS Learner Lab:**
   - AWS Learner Lab จะตัดการทำงานทุก 4 ชั่วโมง เราจึงทำระบบ Checkpoint เซฟไว้บน S3 เมื่อเปิดเครื่องใหม่ โปรแกรมจะทำต่อจากเดือนล่าสุดทันที ไม่ต้องเริ่มนับหนึ่งใหม่
5. **ดักจับและล้างข้อมูลว่างเปล่า (Quality Gate & Data Cleansing):**
   - มีระบบตรวจเช็คไฟล์ หากพบว่าดึงมาแล้วไม่มีตัวเลขวัดจริง (มีแต่ตารางเปล่า) โปรแกรมจะไม่ยอมบันทึกลง S3 และสร้างสคริปต์ `scripts/clean_empty_backfill.py` ไว้สแกนทำความสะอาด S3 ให้ปลอดจากไฟล์ว่างเปล่า

## 4. ขั้นตอนและวิธีคิดในการแก้ปัญหาจริง (Step-by-Step Problem Solving)

ทุกขั้นตอนมาจากการเจอปัญหาหน้างานจริง และแก้ไขอย่างเป็นระบบตามหลักวิศวกรรม:

### ขั้นตอนที่ 1: ตรวจสอบ API จริง และจับคู่สถานี (API Probing & Station Mapping)
- **สิ่งที่พบ:** เว็บ ThaiWater ไม่มีคู่มืออธิบายการใช้งาน เราจึงเขียนโค้ดทดลองยิงเข้าไปดูโครงสร้าง JSON จริง
- **วิธีคิดและแก้ปัญหา:**
  - สกัดข้อมูลจนพบ 8 สถานีวัดระดับน้ำในคลองสายหลักของกรุงเทพฯ (เช่น คลองแสนแสบ, คลองลาดพร้าว, คลองเปรมประชากร)
  - สกัดข้อมูลสถานีวัดน้ำฝน 15 สถานีรอบกรุงเทพฯ
  - เซฟรายชื่อ รหัส พิกัด และความสูงตลิ่งเก็บไว้ใน `reference/stations_water.json` และ `reference/stations_rain.json` เพื่อให้ทุกคนในทีมใช้ชุดข้อมูลเดียวกัน

### ขั้นตอนที่ 2: ระบบดึงข้อมูลสด และการแบ่งถัง S3 (Live Ingestion & Dual-Zone)
- **วิธีคิดและแก้ปัญหา:**
  - ถ้าเก็บข้อมูลรวมกันในโฟลเดอร์เดียว เพื่อนในทีมที่รอรับข้อมูลสดจะรู้ได้ยากว่าไฟล์ไหนคือไฟล์ใหม่ล่าสุด
  - เราจึงแบ่งเป็น 2 ถัง:
    1. `incoming/`: เก็บเฉพาะไฟล์รอบล่าสุด สำหรับให้เพื่อนหยิบไปคำนวณต่อทันที
    2. `raw/`: เก็บแยกโฟลเดอร์ตามวัน (`dt=2026-11-01/`) เพื่อเป็นประวัติศาสตร์ย้อนหลังถาวร
  - **การจัดการฝน:** ข้อมูลฝนของบางสถานีอาจมีหลุดหรือตอบสนองช้า โค้ดถูกเขียนให้ดักจับ Error รายสถานี ถ้าเสีย 1 สถานี อีก 14 สถานีที่เหลือยังถูกบันทึกลง S3 ตามปกติ และระบุสถานะเป็น `PARTIAL` เพื่อแจ้งเตือน

### ขั้นตอนที่ 3: ปัญหาใหญ่! ข้อมูลย้อนหลังกลายเป็นตารางว่างเปล่า 354 ไฟล์
- **สิ่งที่เกิดขึ้นจริง:**
  - หลังจากรันดึงข้อมูลย้อนหลังได้ไฟล์ลง S3 ทั้งหมด 354 ไฟล์ แต่เมื่อเขียนโค้ดเปิดดูข้อมูลข้างใน ปรากฏว่า **"ค่าระดับน้ำเป็น null ว่างเปล่าทุกช่องเวลาทั้ง 354 ไฟล์!"**
  - นอกจากนี้ สถานี 2599 (สามเสน) และ 852087 (อโศก) ยังเจอ Error 500
- **ค้นหาสาเหตุจนเจอ:**
  - API ของ ThaiWater ถ้าเราขอดึงกราฟย้อนหลังโดยไม่ระบุประเภทเซนเซอร์ ระบบจะส่งตารางเวลาเปล่าๆ คืนมาให้ แต่ไม่ยอมดึงตัวเลขวัดจริงมาให้
  - เราแกะระบบจนพบว่า ต้องส่งพารามิเตอร์ `station_type=tele_waterlevel` (ขอข้อมูลจากเสาวัดน้ำดิจิทัล) แนบไปด้วยเสมอ
- **วิธีแก้ปัญหา:**
  1. แก้ไขไฟล์ `src/thaiwater_client.py` ให้ส่ง `station_type=tele_waterlevel`
  2. ใส่ตัวตรวจคุณภาพ (Quality Gate) ใน `src/backfill.py` ถ้าสถานีไหนได้ค่าว่างล้วน ห้ามบันทึกลง S3 เด็ดขาด
  3. เขียนสคริปต์ `scripts/clean_empty_backfill.py` เพื่อสแกนและลบไฟล์ขยะ 354 ไฟล์ทิ้งทั้งหมดจาก S3
  4. รันดึงข้อมูลใหม่ รอบนี้ได้ตัวเลขระดับน้ำจริงเฉลี่ยเดือนละ 4,200 กว่าแถวต่อสถานี และไม่มี Error 500 อีกเลย

### ขั้นตอนที่ 4: การพิสูจน์ความถี่ 10 นาทีทางคณิตศาสตร์ (10-Minute Resolution Proof)
- **เป้าหมาย:** พิสูจน์ให้เห็นจริงว่าข้อมูลที่ดึงมา วัดละเอียดทุก 10 นาทีจริง ไม่ใช่การนำค่าเฉลี่ยรายวันมาหารเฉลี่ย
- **การทดสอบจริง:**
  - รันสคริปต์ `scripts/verify_telemetry_resolution.py` วัดผลต่างของเวลา ($\Delta t = t_i - t_{i-1}$)
  - ผลลัพธ์: ตลอดทั้งเดือนกันยายน 2026 มีช่องเวลา 4,320 ช่องเวลา ค่าเวลาขยับทีละ **10.0 นาทีเต็ม 100.0%** (4,319 รอยต่อ) และมีตัวเลขวัดจริงถึง 4,293 แถว (สมบูรณ์ 99.38%)

### ขั้นตอนที่ 5: รับมือกับเวลาตัดรอบ 4 ชั่วโมงของ AWS Learner Lab
- **ข้อจำกัด:** AWS บัญชีนักศึกษาจะตัดการทำงานและปิดเครื่องทุกๆ 4 ชั่วโมง
- **วิธีคิดและแก้ปัญหา:**
  - สร้างไฟล์ Checkpoint เก็บไว้บน S3 (`raw/thaiwater/checkpoint.json`)
  - ทุกครั้งที่ดึงข้อมูลเดือนไหนเสร็จ จะบันทึกลง Checkpoint ทันที
  - เมื่อเปิดเครื่องใหม่แล้วรันคำสั่งเดิม โปรแกรมจะตรวจเช็คก่อน ถ้างวดไหนทำเสร็จแล้วจะข้ามไปทำเดือนถัดไปทันที ทำให้ดึงข้อมูลต่อได้เรื่อยๆ โดยไม่ต้องเริ่มนับหนึ่งใหม่

### ขั้นตอนที่ 6: ไขข้อข้องใจ ทำไมค้นหา Rule ใน AWS Console แล้วไม่เจอ
- **สาเหตุ:** AWS ได้ปรับปรุงหน้าจอ EventBridge ใหม่ โดยแยกกฎที่ตั้งเวลาด้วย cron/rate ออกจากหน้า Rules ทั่วไป ย้ายไปอยู่ที่เมนู **`Scheduler > Scheduled rules (legacy)`**
- ในระบบจริง กฎทั้ง 2 ทำงานเปิดใช้งาน (`ENABLED`) ปกติ และสามารถตรวจสอบผ่าน AWS CLI ได้ตลอดเวลา

### ขั้นตอนที่ 7: อธิบายที่มาของรหัสสถานีทั้ง 8 แห่ง
หลายคนอาจสงสัยว่าทำไมรหัสสถานีถึงมีทั้งเลขหลักเดียว (1, 3, 4), เลข 4 หลัก (2599), และเลข 6 หลัก (852087):
- **เลข 1–2 หลัก (`1, 3, 4, 5, 8, 10`):** สถานีโทรมาตรหลักของ **สสน. (HII)** ในคลอง กทม. วัดละเอียดทุก 10 นาที ($4,320\text{ ช่อง/เดือน}$)
- **เลข 4 หลัก (`2599`):** สถานี C.12 ของ **กรมชลประทาน (RID)** ตรงชลประทานสามเสนริมแม่น้ำเจ้าพระยา ส่งข้อมูลเป็นราย 1 ชั่วโมง ($720\text{ ช่อง/เดือน}$)
- **เลข 6 หลัก (`852087`):** สถานีความร่วมมือของ **สถาบัน AIT** ตรงคลองแสนแสบอโศก วัดละเอียดทุก 10 นาที

## 5. ตัวอย่างโค้ดคำสั่งสำคัญพร้อมคำอธิบาย (Code & Verification)

### 5.1 โค้ดตรวจสอบความสมบูรณ์ของ 8 สถานีใน S3
คำสั่งนี้ใช้รันบน CloudShell เพื่อดึงข้อมูลจริงใน S3 มานับแถวที่มีตัวเลขจริง และดูค่าระดับตลิ่ง:

```python
# คำสั่ง Python ตรวจสอบข้อมูลระดับน้ำจริงใน S3
import json, boto3

s3 = boto3.client("s3")
BUCKET_NAME = "cs341-tuamyang-data"
FOLDER_PREFIX = "raw/thaiwater/waterlevel/dt=2026-09-01/"

# วนลูปอ่านไฟล์ของทุกสถานีในเดือนกันยายน 2026
for obj in s3.list_objects_v2(Bucket=BUCKET_NAME, Prefix=FOLDER_PREFIX).get("Contents", []):
    # อ่านไฟล์ JSON จาก S3
    doc = json.loads(s3.get_object(Bucket=BUCKET_NAME, Key=obj["Key"])["Body"].read())
    station_id = doc.get("api_station_id")
    records = doc.get("data", [])
    
    # นับจำนวนแถวที่มีตัวเลขระดับน้ำจริง (ไม่เป็นค่าว่างหรือ null)
    non_null_count = sum(1 for row in records if row.get("waterlevel_msl") not in (None, ""))
    
    # ดึงค่าระดับตลิ่ง (min_bank) ของสถานีนี้
    min_bank = records[0].get("min_bank_msl") if records else None
    
    # แสดงผลลัพธ์
    print(f"สถานี {station_id:>6}: ช่องเวลาทั้งหมด={len(records):>4}, มีข้อมูลจริง={non_null_count:>4}, ระดับตลิ่ง={min_bank} ม.รทก.")
```
