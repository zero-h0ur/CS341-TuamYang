# ThaiWater Data Contract & Interface Specification
> **เจ้าของเอกสาร:** สมาชิกคนที่ 1 (ThaiWater Ingestion) — นายภูริณัฐ วรรธนะธัญญา (`PurinatWanthanathanya`)  
> **กลุ่มเป้าหมาย:** สมาชิกคนที่ 3 (Reference & Spatial Join), สมาชิกคนที่ 4 (Orchestration & Validation), สมาชิกคนที่ 5 (Curated & Analysis)  
> **อัปเดตล่าสุด:** ปรับปรุงความละเอียดข้อมูลโทรมาตรระดับน้ำจริง **10 นาที** (ยืนยันผ่าน `station_type=tele_waterlevel`), แก้ไขความสูงตลิ่งจริง (min_bank 0.62–2.39m MSL), ดึงข้อมูลย้อนหลังครบทั้ง 8 สถานีตั้งแต่ปี 2565

## 1. วัตถุประสงค์และสรุปการค้นพบสำคัญ (Important Discoveries)
1. **ความละเอียดของข้อมูลโทรมาตรระดับน้ำ (Telemetry Data Resolution):**  
   จากการทดสอบดึงข้อมูลจริงของ ThaiWater ผ่านพารามิเตอร์ `station_type=tele_waterlevel` พบว่าระดับน้ำโทรมาตรส่งข้อมูลทุก **10 นาที** (สอดคล้องกับข้อเสนอใน Proposal 100%)
   - **สถานีโทรมาตรคลองหลัก 7 สถานี (ID 1, 3, 4, 5, 8, 10, 852087):** ส่งข้อมูลทุก 10 นาที (144 เรคคอร์ด/วัน, 6 แถว/ชั่วโมง, ~4,320 แถวต่อเดือน 30 วัน หรือ 4,464 แถวต่อเดือน 31 วัน)
   - **สถานีชลประทานสามเสน (C.12 / ID 2599):** เป็นสถานีตรวจวัดรายชั่วโมง (24 เรคคอร์ด/วัน, 1 แถว/ชั่วโมง, 720 แถวต่อเดือน 30 วัน)
   - **ข้อกำหนดสำคัญของ API สสน. (`station_type=tele_waterlevel`):** การเรียก endpoint `/waterlevel_graph` **ต้องระบุ `station_type=tele_waterlevel` เสมอ** หากไม่ระบุ API จะคืนกริดตารางจำลองที่ค่า `value` เป็น null ทั้งหมด และส่งผลให้สถานี 2599/852087 คืนค่า HTTP 500
   - **คำแนะนำสำหรับสมาชิก 5 (Curated):** ในการทำ Hourly Roll-up (`khwaeng_hourly`) จะมีข้อมูลระดับน้ำคลอง 6 แถวต่อชั่วโมง (และ 1 แถวต่อชั่วโมงสำหรับ C.12)
2. **Timezone:**  
   พาทและเวลาทั้งหมดของ ThaiWater อยู่ใน **เวลาประเทศไทย (UTC+7 / Asia/Bangkok)**  
   - `dt=YYYY-MM-DD` และ `hour=HH` เป็นเวลาไทย
   - ฟิลด์ `timestamp_epoch` (Unix timestamp ในหน่วยวินาที) เป็นสากล ใช้สำหรับ Join ข้ามระบบกับ Traffy (ซึ่งบันทึกเป็น UTC) ได้โดยตรง
3. **การ Deduplication สำหรับสมาชิก 4 และ 5:**  
   ไฟล์ Raw Live Ingestion มี Batch ID กำกับเพื่อการตรวจสอบ แต่หากมีการดึงซ้ำ ให้ใช้คู่คีย์ `(api_station_id, timestamp_epoch)` เป็น Composite Primary Key ในการ Deduplicate
4. **ความสูงตลิ่งและระยะพ้นตลิ่ง (Freeboard / `diff_wl_bank_m`):**  
   $$\text{Freeboard } (\text{diff\_wl\_bank\_m}) = \text{min\_bank\_msl} - \text{waterlevel\_msl}$$
   - ค่าบวก ($>0$) = ระดับน้ำอยู่ต่ำกว่าสันตลิ่ง (น้ำยังไม่ล้น ยิ่งค่าน้อยยิ่งเสี่ยงล้น)
   - ค่าลบ ($<0$) = ระดับน้ำล้นตลิ่ง (น้ำท่วมขัง)

## 2. โครงสร้าง Storage Partition (Dual-mode: S3 / Local)

```text
raw/
└── thaiwater/
    ├── waterlevel/
    │   ├── dt=YYYY-MM-DD/hour=HH/waterlevel_{batch_id}.json          # Real-time ดึงสดทุก 15 นาที
    │   └── dt=YYYY-MM-01/waterlevel_hist_st{station_id}_{YYYY}_{MM}.json # Backfill ประวัติรายเดือน

        ├── dt=YYYY-MM-DD/hour=HH/rain_{batch_id}.json                # Real-time ฝนสะสม 24 ชม. ดึงสดทุก 1 ชม.
        └── dt=YYYY-MM-01/rain_monthly_st{station_id}_{YYYY}_{MM}.json    # Backfill ฝนรายวันรายเดือน
```

### นิยามและการคำนวณระยะพ้นตลิ่ง (Freeboard / `diff_wl_bank_m`)
$$\text{Freeboard } (\text{diff\_wl\_bank\_m}) = \text{min\_bank\_msl} - \text{waterlevel\_msl}$$
- **ค่าเป็นบวก ($>0$):** ระดับน้ำต่ำกว่าสันตลิ่ง (น้ำยังไม่ล้นคลอง ยิ่งค่าน้อย แปลว่าน้ำยิ่งใกล้ล้น)
- **ค่าเป็นลบ ($<0$):** ระดับน้ำสูงกว่าสันตลิ่ง (น้ำล้นตลิ่ง/ท่วมพื้นที่ริมคลอง)
- **ฟิลด์ `diff_source`:**
  - `"api"`: ดึงจากฟิลด์ `diff_wl_bank` ของ ThaiWater API โดยตรงสำหรับ Live Ingestion
  - `"derived"`: คำนวณจากสูตรข้างต้นสำหรับ Historical Backfill โดยกำหนดสมมติฐานว่าความสูงตลิ่งของแต่ละสถานีมีค่าคงที่ตลอดช่วง 2565–ปัจจุบัน
- **Outlier ภาษีเจริญ (ID 10):** ระดับน้ำรายงานที่ -6.11 m MSL ทำให้มีระยะพ้นตลิ่ง $1.42 - (-6.11) = 7.53\text{ m}$ ซึ่งตรงกับค่าของ API สสน. ทุกประการ ให้คงค่าจริงนี้ไว้ตามข้อมูลต้นทาง (สมาชิกคนที่ 4 สามารถใช้เงื่อนไขตรวจสอบ $>5\text{ m}$ ได้ตามปกติ)

## 5. การคัดเลือกสถานีวัดน้ำฝน 15 สถานี (Rain Telemetry Stations)
ในกรุงเทพฯ มีสถานีวัดน้ำฝนทั้งหมด 134 สถานีใน ThaiWater แต่การทำ Ingestion และ Backfill มุ่งเน้น **15 สถานีโทรมาตรที่ใกล้ที่สุดกับสถานีระดับน้ำทั้ง 8 สถานี (Nearest Rain Telemetry Stations)**
- **เหตุผลการคัดเลือก:**
  1. **สอดคล้องกับ Q1 และงานของสมาชิกคนที่ 3:** ในขั้นตอน Spatial Join สมาชิกคนที่ 3 จะต้องจับคู่สถานีระดับน้ำเข้ากับสถานีวัดน้ำฝนที่ใกล้ที่สุด (Nearest Neighbor) การเลือก 15 สถานีนี้ครอบคลุมรัศมีรอบสถานีระดับน้ำคลองหลักทั้งหมด
  2. **ลดภาระ API และ Network:** การดึงข้อมูลประวัติรายเดือนจาก 134 สถานีย้อนหลังถึงปี 2565 จะสร้าง Request กว่า 7,000 requests ต่อ Public API ของ สสน. ซึ่งเสี่ยงต่อการโดน Rate limit หรือบล็อก IP การจำกัดเหลือ 15 สถานีหลักทำให้ได้ข้อมูลที่แม่นยำและเสถียร 100%
  3. **รายชื่อสถานีฝน 15 แห่ง:** บันทึกไว้อย่างชัดเจนใน `reference/stations_rain.json`

## 6. การแก้ไขปัญหาการดึงข้อมูลย้อนหลัง (`station_type=tele_waterlevel`)
เดิมการเรียก `/waterlevel_graph` โดยไม่ระบุ `station_type` ส่งผลให้:
1. สถานีคลองแสนแสบ (`852087`) และชลประทานสามเสน (`2599`) คืนค่า HTTP 500
2. อีก 6 สถานีคืนค่าตารางจำลองที่มีแต่ช่องเวลาโดย `value` เป็น null ทั้งหมด
**แนวทางแก้ไขที่ยืนยันแล้ว:**  
เมื่อเพิ่มพารามิเตอร์ `station_type=tele_waterlevel` เข้าไปใน Request:
- ทั้ง 8 สถานีคืนค่า telemetry ที่วัดได้จริง 100% ครอบคลุมตั้งแต่ปี 2565 ถึงปัจจุบัน
- สถานี 2599 และ 852087 หายจากปัญหา HTTP 500 โดยดึงข้อมูลได้สมบูรณ์ (2599 ได้ 687 ค่า/เดือน, 852087 ได้ 4,161 ค่า/เดือน)
- ค่า `min_bank` ถูกส่งกลับมาจาก API โดยตรงตรงกับข้อมูลอ้างอิงที่แก้ไขแล้วทุกประการ

## 7. กรณีศึกษาความสดของข้อมูล (Data Freshness Case Study สำหรับสมาชิกคนที่ 4)
จากการสังเกตข้อมูลสดจริง พบว่าสถานี **C.12 (กรมชลประทานสามเสน)** รายงานเวลาตรวจวัดล่าสุดที่ 23:00 น. ในขณะที่อีก 7 สถานีรายงานเวลาที่ 01:10 น. (ข้อมูลค้างช้ากว่าเวลาปัจจุบันเกิน 2 ชั่วโมง)
- ปรากฏการณ์นี้ตรงกับที่ Proposal วางสมมติฐานไว้ว่า เซ็นเซอร์โทรมาตรบางแห่งอาจเกิดปัญหาดีเลย์ในการส่งสัญญาณ
- สมาชิกคนที่ 4 (Orchestration & Validation) สามารถใช้เงื่อนไข:
  $$\Delta t = |\text{ingested\_at\_bkk} - \text{waterlevel\_datetime}| > 1 \text{ ชั่วโมง}$$
  เพื่อปักธง Data Freshness Warning ได้อย่างสมบูรณ์

## 8. โครงสร้างข้อมูลน้ำฝนสด (Rain Telemetry & Sliding Window Contract)

### 8.1 ลักษณะข้อมูลจาก ThaiWater `/rain_24h_graph`
API สสน. ส่งข้อมูลย้อนหลังประมาณ 36–37 จุดรายชั่วโมง (ครอบคลุมตั้งแต่เที่ยงคืนของเมื่อวานจนถึงชั่วโมงปัจจุบัน):
1. **ค่าฝนรายชั่วโมง (Incremental Hourly Rainfall):** แต่ละจุด (`rain_mm`) คือปริมาณน้ำฝนที่ตกใน 1 ชั่วโมงนั้นจริง ๆ ไม่ใช่ยอดสะสม
2. **การคำนวณยอดฝน 24 ชั่วโมง (`rain_24h_mm`):**  
   $$\text{rain\_24h\_mm} = \sum_{i=1}^{24} \text{rain\_mm}_i \quad (\text{ผลรวมของ 24 จุดล่าสุดที่มีค่า})$$
   - `rain_24h_points`: จำนวนจุดที่นำมาคำนวณ (ควรมี 24 จุด หากน้อยกว่า 24 แปลว่ามีบางชั่วโมงที่เซ็นเซอร์ยังไม่รายงาน)
   - `series`: อาร์เรย์ของจุดข้อมูลรายชั่วโมงทั้งหมด `[{"datetime": "YYYY-MM-DD HH:MM", "rain_mm": float | null}]`
3. **การจัดการค่าว่าง (Null Handling):** หากจุดใดยังไม่มีการวัด จะส่งค่าเป็น `null` (`None`) ไม่ถูกแปลงเป็น `0.0` เพื่อป้องกันข้อมูลบิดเบือน
4. **ความสดของข้อมูลน้ำฝน (Rain Freshness SLA):**  
   เนื่องจากเซ็นเซอร์น้ำฝนรายงานเป็นรอบรายชั่วโมงและจุดชั่วโมงล่าสุดอาจยังว่างอยู่ (เช่น ดึงตอน 12:16 น. จุด 12:00 น. อาจยังเป็น `null`) เกณฑ์ Freshness SLA ของฝนควรกำหนดไว้ที่ **2–3 ชั่วโมง**

### 8.2 การทับซ้อนของไฟล์รายชั่วโมงและการ Deduplicate (สำหรับสมาชิกคนที่ 4 และ 5)
- ไฟล์รายชั่วโมงใน `raw/thaiwater/rain/dt=.../hour=.../` จะมีช่วงเวลาเหลื่อมซ้อนกัน (Overlapping 36-hour sliding window)
- ในการรวบรวมข้อมูลรายชั่วโมง ให้ใช้ข้อมูลจาก **Batch ล่าสุด** ของแต่ละชั่วโมงเป็นหลัก (`latest batch wins`) เพื่อให้ได้ข้อมูลที่สมบูรณ์ที่สุด
- ⚠️ **แจ้งเตือนสำคัญสำหรับสมาชิกคนที่ 4 และ 5:**  
  ไฟล์ฝนที่ถูกดึงก่อนการปรับปรุงระบบนี้ (ไม่มีฟิลด์ `series`) เป็นการรวมทุกจุด 36 จุด ซึ่งสูงกว่ายอด 24 ชม. จริง ให้หลีกเลี่ยงการใช้ `rain_24h_mm` จากไฟล์ช่วงก่อนหน้านั้น และให้เริ่มใช้ไฟล์ที่มีฟิลด์ `series` และ `rain_24h_points` ตั้งแต่บัดนี้เป็นต้นไป
